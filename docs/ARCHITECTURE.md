# Архитектура HyRouter

HyRouter — HyRoute для роутеров на OpenWrt: раздельная маршрутизация трафика
всей домашней сети через серверы Hysteria 2 и VLESS. Что идёт через VPN, что
напрямую, а что блокируется, решают правила по **устройствам** сети, сайтам,
IP, портам и спискам geosite/geoip. Устройства в сети ничего не настраивают.

Документ — план, принятый до кода. Решения, которые ещё предстоит проверить на
железе, отмечены как допущения.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Роутеры | OpenWrt 24.10 и новее с fw4 (nftables). Две редакции из одного кода ([«Редакции»](#редакции)): **HyRouter** — aarch64 и x86_64, 256+ МБ RAM; **HyRouter Lite** — MIPS MT7621 (`mipsel_24kc`) и ARMv7 IPQ40xx (`arm_cortex-a7_neon-vfpv4`), 256 МБ RAM (128 МБ — с оговорками). MT7628/MT7620 с 64 МБ не поддерживаются |
| Правила | Как в HyRoute, но вместо программы — устройство (MAC, при необходимости IP). Сайты, IP и сети, geosite/geoip, протокол и порты, сервер или группа, запасные серверы, «Всё остальное» |
| Управление | Свой веб-интерфейс на Svelte 5, встроенный в бинарник. LuCI не используется |
| Код HyRoute | Нужные пакеты копируются из HyRoute (MIT) в этот репозиторий, у каждого — отметка коммита-источника ([«Код из HyRoute»](#код-из-hyroute)) |
| Ядра | Официальные `hysteria` и `xray` для linux-arm64/amd64 (Lite: `hysteria` для linux-mipsle-sf и linux-arm), версии и SHA-256 закреплены в `build/deps.json`, как в HyRoute; в пакет не входят, скачиваются при первой необходимости |

## Редакции

Обе редакции собираются из одного кода; Lite — с тегом сборки `lite`
(`internal/edition`), пакет `hyrouter-lite` (конфликтует с `hyrouter`).

| | HyRouter | HyRouter Lite |
|---|---|---|
| Архитектуры | `aarch64_cortex-a53`, `aarch64_generic`, `x86_64` | `mipsel_24kc` (`GOARCH=mipsle GOMIPS=softfloat`), `arm_cortex-a7_neon-vfpv4` (`GOARCH=arm GOARM=7`) |
| Протоколы | Hysteria 2, VLESS (Xray) | Hysteria 2 |
| Ядра | `/usr/share/hyrouter/bin` | там же, если на флеше 32+ МБ свободно, иначе `/tmp/hyrouter/bin` (RAM, скачивается заново после перезагрузки) |
| Кэш DNS | 50 000 записей | 10 000 записей |
| Память hyrouterd | без ограничения | `GOMEMLIMIT` 48 МБ |
| Одновременных соединений через relay | 8192 | 2048 |

- На слабом процессоре узкое место — шифрование в ядре VPN (Hysteria, Xray).
  Прямой трафик решает ядро Linux, и HyRouter его не замедляет: это главное,
  что делает Lite возможной.
- **Позже для Lite:** клиент Hysteria внутри hyrouterd (библиотека
  `apernet/hysteria/core`, MIT) вместо отдельного процесса — один рантайм Go
  и ~20 МБ вместо ~35 МБ на флеше; редакция «только обход DPI» без VPN для
  роутеров со 128 МБ и 16 МБ флеша.

## Как идёт трафик

```
устройство LAN ──► br-lan ──► nftables: таблица inet hyrouter (prerouting)
                                │  чьё: ether saddr / ip saddr из наборов устройств
                                │  куда: наборы адресов правил (IP, geoip, адреса из DNS)
                                │  правила сверху вниз, первое совпадение
                                ├─ Напрямую ───► обычная маршрутизация ядра (и flow offload)
                                ├─ Блок ───────► reject (TCP reset) / drop (UDP)
                                └─ VPN / нужен домен ─► TPROXY в hyrouterd
                                                    ├─ relay TCP: SNI/Host при необходимости,
                                                    │   SOCKS5 CONNECT в hysteria/xray
                                                    └─ UDP: SOCKS5 UDP ASSOCIATE
```

Главное отличие от HyRoute: решение принимает **ядро**, а не пакетный цикл в
пользовательском пространстве. Процессор роутера слабый, и прямой трафик
(обычно большая часть) не должен проходить через hyrouterd. Поэтому правила
компилируются в цепочку nftables, а трёхзначная оценка HyRoute
(`Final` / `NeedsDomain`) переносится на этап компиляции:

- правило, итог которого известен по устройству, IP, порту и протоколу, — это
  правило nftables с вердиктом: прямой трафик остаётся в ядре;
- правило по сайтам срабатывает по адресам, которые этим сайтам выдал DNS
  ([«DNS»](#dns)): наборы с таймаутом записи по TTL;
- адрес, имена которого дают разные маршруты (общий IP CDN), попадает в набор
  «нужен домен», и такие соединения идут в relay, который читает SNI/Host, как
  режим SNIFF в HyRoute. Если по имени выходит «Напрямую», relay сам
  подключается к адресу с меткой обхода.

### nftables и policy routing

- Своя таблица `inet hyrouter`, а не правила внутри `inet fw4`: fw4 при
  перезагрузке пересоздаёт только свою таблицу, и наша её переживает. Удаление
  таблицы снимает весь перехват одной операцией.
- Перехват — только `prerouting` с LAN-интерфейсов (по умолчанию `br-lan`).
  Собственный трафик роутера (в том числе ядер к серверам) не перехватывается,
  поэтому исключать адреса серверов не нужно.
- TPROXY для TCP и UDP, IPv4 и IPv6 (`kmod-nft-tproxy`). Метка пакета и
  `ip rule fwmark … lookup <таблица>` с `local default dev lo` доставляют
  пакет на сокет hyrouterd с `IP_TRANSPARENT`. Прямые подключения relay идут
  с отдельной меткой и мимо перехвата.
- Обязательные исключения стоят первыми в цепочке: локальные и частные сети,
  multicast/broadcast, адреса самого роутера, DHCP.
- **Допущение:** программный и аппаратный flow offload fw4 ускоряет только
  пересылаемые соединения (хук forward). Соединения, отданные в TPROXY,
  доставляются локально и под offload не попадают, прямые — попадают. Проверить
  на железе с аппаратным offload (MediaTek).

## DNS

На роутере HyRouter видит все DNS-запросы сети, поэтому DNS — основной источник
имён (в HyRoute он был пассивным и вспомогательным).

- Запросы устройств на порт 53 роутера перенаправляются (`redirect` в своей
  таблице) на DNS hyrouterd. Он отвечает по DNS-политикам HyRoute
  (`dnspolicy`): имена «через VPN» разрешаются через сервер правила, «блок» —
  NXDOMAIN, остальное и локальные имена (`*.lan`, имена из DHCP) — как раньше,
  через dnsmasq роутера.
- Каждый ответ раскладывает адреса по наборам правил, с которыми совпало имя,
  с таймаутом по TTL (с теми же нижней и верхней границей, что DNS-кэш HyRoute).
  Известно и устройство, которое спрашивало: для правил «устройство + сайт»
  адрес попадает в набор пары.
- Устройства, которые ходят в обход DNS роутера (свой DoH/DoT, жёстко заданный
  DNS), видны только по SNI. Как в HyRoute: «Не давать обходить DNS» блокирует
  известные DoH/DoT и перехватывает чужой UDP/TCP 53, а «Точное определение
  сайта» отправляет веб-порты таких устройств в relay.

## Отказы

Правила HyRoute, которые не нарушаются, сохраняются:

- **VPN-трафик никогда не уходит напрямую.** Сервер недоступен, группа пуста,
  hyrouterd упал — соединение отклоняется или идёт через запасной сервер.
  Если процесс упал, таблица nftables остаётся: TPROXY-соединения не находят
  сокет и сбрасываются, а прямой трафик работает, потому что его решает ядро.
  procd перезапускает hyrouterd.
- **Прямой трафик не зависит от VPN** и от hyrouterd.
- **Штатная остановка** (`/etc/init.d/hyrouter stop`, удаление пакета) снимает
  таблицу и правила маршрутизации: сеть работает как без HyRouter.
- **Допущение:** при загрузке роутера до старта hyrouterd таблицы нет и трафик
  идёт напрямую. Kill switch на это время — отдельная задача (блок через
  include fw4 до первого запуска).

## Обход DPI (zapret2)

Как «Обход DPI» в HyRoute 1.3.25, только для всей сети: YouTube, Discord и
свои сайты открываются напрямую, без VPN, через `nfqws2` из
[zapret2](https://github.com/bol-van/zapret2) v1.0.7 (`internal/zapret`, код
из HyRoute — [hyroute-sync.md](hyroute-sync.md)).

- **Что видит nfqws2.** Только трафик, который уходит с роутера в интернет
  напрямую: прямые соединения устройств и самого роутера. Туннель идёт к
  серверам, а их адреса исключены дважды: в правилах nftables (наборы
  `zapret_skip4/6`) и в каждом профиле nfqws2 (`--ipset-exclude`). Правила
  «Обход DPI: …» наверху профиля правил, как в HyRoute, держат эти сервисы
  на прямом пути. Сайты сервиса в них — с поддоменами (`.youtube.com`:
  и `www.youtube.com`, и видеосерверы), адреса — как есть.
- **Правила nftables** (`zapret.NFT`) повторяют режим postnat самого zapret2
  (`common/nft.sh`): исходящие — после NAT (`postrouting`, приоритет 101),
  ответы — до него (`prerouting`, −101), только первые пакеты соединения
  (20 TCP, 5 UDP), в очередь 200. Из ответов — всегда SYN-ACK: по его TTL
  nfqws2 считает «TTL по расстоянию» (`ip_autottl`), без него фейк уходит с
  обычным TTL, доходит до сервера и ломает соединение. При переборе методов —
  первые 10 ответов, их читает детектор неудач. Свои пакеты
  nfqws2 помечает `0x40000000` и не попадает в очередь снова, а их conntrack не
  отслеживает (цепочка `predefrag`, как у zapret2).
- **Командная строка** (`zapret.Build`) — те же проверенные блоки, что у
  winws2 в HyRoute, но вместо фильтров WinDivert `--qnum`, `--fwmark` и
  `--user=daemon`: очередь nfqws2 открывает под root и дальше работает без
  прав. Текст пользователя в аргументы не попадает.
- **Методы и списки** — как в HyRoute 1.3.23: 11 готовых методов, из них три
  под «белым» именем vk.com против обрыва «16–20 КБ» у адресов Cloudflare
  (вложения и видео Discord). Фейки готовых методов «портятся» TCP MD5 (и
  старой меткой времени) или TTL: устройство сети с Windows меток времени не
  ставит, и фейк, испорченный только ими, дошёл бы до сервера. В списке
  Discord для `nfqws2` — внешнее имя ECH `cloudflare-ech.com`. В правила
  «Обход DPI: …» оно не входит: иначе напрямую пошёл бы любой сайт
  Cloudflare с ECH.
- **Генератор стратегий** (`zapret.Strategy`): когда готовые методы не
  помогли, подбор собирает варианты из приёмов zapret2 (фейк, способ его
  испортить, разрез и его место, перекрытие, подмена имени): соседей
  сработавшего метода и разброс по всем приёмам. Фейки с ClientHello сайтов
  из белого списка (ya.ru, gosuslugi.ru, max.ru, 4pda.to, ozon.ru) HyRouter
  делает сам (utls) рядом со списками. Стратегия хранится как ID
  (`g:f=w_ya_ru;o=md5;…`) и читается только из фиксированных значений: в
  командную строку `nfqws2` по-прежнему не попадает текст пользователя.
- **Свои сайты** — имена и публичные IP-адреса или подсети (не шире /8 для
  IPv4 и /16 для IPv6; адреса LAN и служебные сети не принимаются). Адреса
  идут в `sites-ip.txt` и свой профиль с `--ipset`, с тем же планом методов;
  подбор проверяет только имена. Сначала он открывает до 20 своих сайтов без
  обхода: те, что не открываются и так (имени нет в DNS, блок по адресу),
  пропускает, называет и запоминает для сети (`Picked.SkippedSites`), а для
  остальных подбирает метод.
- **Подбор** идёт с самого роутера, с портов 30000–31949 (ниже эфемерных
  портов Linux): слот 0 — без обхода, слот i — в очередь 200+i, где свой
  nfqws2 пробует метод i (и получает SYN-ACK своих проверок). Обход сети этих
  портов не видит и во время подбора не останавливается.
- **Самопроверка** (как в HyRoute 1.3.25, делает контроллер, этап 4): раз в
  10 минут hyrouterd открывает сервисы через работающий обход с обычного
  порта роутера (`zapret.Live`); если сервис перестал открываться, а
  блокировку можно обойти, подбор запускается заново. Второго подбора нет,
  если за время проверки сеть уже подобрали («Подобрать»), а на сети без
  подбора он идёт, только когда сервис открывается без обхода или его можно
  обойти: без интернета пустой результат не запоминается. Настройки обхода
  проверка и страница читают из своей копии, под блокировкой.
- **«Через VPN»** даёт выбрать сервер или группу (`Settings.Via`); удалённый
  сервер или группа заменяется основным сервером. «По вашим правилам»
  уступает сервис правилам пользователя, только если они ведут через VPN все
  его сайты (спрашивается имя под каждым сайтом, адреса — никогда); иначе
  своё правило ведёт остальное через выбранный сервер, а голос Discord
  (адреса без имён) — через основной.
- **Файлы.** `nfqws2` (статический, ~320 КБ), три библиотеки Lua и три
  фейковых пакета (ClientHello google.com и vk.com, QUIC Initial) входят в
  пакет HyRouter и сверены с `build/deps.json`;
  CI запускает настоящий `nfqws2 --dry-run` с каждой командной строкой
  (готовые методы, сгенерированные стратегии, свои сайты по адресам) и
  проверяет правила через `nft -c`.
- **Ограничение:** с программным или аппаратным flow offloading fw4 первые
  пакеты пересылаемых соединений могут уйти мимо очереди. hyrouterd будет
  предупреждать об этом на странице обхода (этап 4).

## Процессы и файлы

| Что | Где |
|---|---|
| `hyrouterd` | `/usr/bin/hyrouterd`, служба procd `/etc/init.d/hyrouter` с respawn, root |
| Ядра | по одному `hysteria` или `xray` на используемый сервер, дочерние процессы с `Pdeathsig` |
| Настройки | `/etc/hyrouter/*.json` (правила, серверы, подписки, группы, устройства), `0600`; сохраняются при sysupgrade (`/lib/upgrade/keep.d/hyrouter`) |
| Базы geo, ядра | `/usr/share/hyrouter` или внешний носитель: скачиваются при первой необходимости и сверяются по SHA-256 |
| Временное | `/tmp/hyrouter`: конфиги ядер, журналы (RAM: флеш не изнашивается) |
| Статистика | по устройствам, серверам и группам, без сайтов; запись на флеш редкая (раз в час и при остановке) |

## Веб-интерфейс

- Svelte 5 + TypeScript, сборка встраивается в `hyrouterd` (`go:embed`), собранный
  `web/dist` коммитится, как `frontend/dist` в HyRoute.
- Слушает только LAN-адреса роутера, порт настраивается.
- **Вход — паролем root роутера** через rpcd (`ubus session login`), без
  отдельной учётной записи. Сессия в cookie, CSRF-токен, ограничение попыток.
- Страницы: Главная, Правила, Устройства, Серверы, Подписки, Группы,
  Соединения, Журнал, Настройки. Где возможно, вид и логика берутся из окна
  HyRoute.

## Код из HyRoute

Источник — `github.com/lardan099/hyroute`, сверено с `01032d2` (v1.3.25). Пакеты
HyRoute лежат в `internal/` и не импортируются, поэтому копируются. Какой
пакет с какого коммита взят и чем отличается, записано в
[hyroute-sync.md](hyroute-sync.md): по нему переносятся исправления.

| Берём как есть или почти | Переделываем | Не нужно |
|---|---|---|
| `hy2uri`, `vless`, `subfmt`, `geodata`, `ruleconv`, `socks5`, `sniff`, `dnscache`, `dnsproxy`, `logx`, `release` | `rules` (программы → устройства), `hysteria` и `tunnels` (запуск процессов на Linux), `groups`, `relay` (TPROXY вместо reflect-NAT), `dnspolicy`, `stats`, `store` | `divert`, `packet`, `attrib`, `procinfo`, `killswitch`, `engine`, `uirpc`, `autostart`, `netwatch`, `sysdns`, Wails |

## Сборка и пакеты

- `CGO_ENABLED=0 GOOS=linux`, статический бинарник: HyRouter —
  `GOARCH=arm64|amd64`, Lite — `-tags lite` с `GOARCH=mipsle GOMIPS=softfloat`
  и `GOARCH=arm GOARM=7`.
- Пакеты для OpenWrt: `.ipk` (opkg, 24.10) и `.apk` (apk-tools, выпуски
  после 24.10). Зависимости: `kmod-nft-tproxy`, `kmod-nft-socket`, `kmod-nft-queue` (обход DPI),
  `ca-bundle`. Архитектуры пакетов — в [«Редакции»](#редакции).
- Релиз собирает CI по тегу: пакеты обеих редакций, `SHA256SUMS`, заметки
  к выпуску (`docs/release-notes/vX.Y.Z.md`). Выпуски до 1.0 — бета
  (pre-release на GitHub).

## Тесты

- `go test ./...` на Linux в CI.
- Интеграционный тест в CI в сетевых пространствах имён: «устройство» →
  «роутер» с hyrouterd и настоящими nftables/TPROXY → «интернет» с заглушкой
  SOCKS5 и DNS. Проверяет прямой путь, туннель, блок, домен из DNS и из SNI,
  отказ ядра и падение hyrouterd.
- Смоук-тест пакета в CI: образ OpenWrt x86_64 в QEMU, установка `.ipk`,
  старт службы, ответ веб-интерфейса.
- Всё проверяется только в CI на GitHub: на ПК мейнтейнера нет Go, и тесты
  там не запускаются (см. CLAUDE.md). Проверка на настоящем роутере —
  вручную, по списку в issue перед выпуском.

## Этапы

1. **Основа.** Репозиторий, CI, скопированные пакеты HyRoute собираются и
   проходят свои тесты на Linux.
2. **Маршрутизация без интерфейса.** Компилятор правил в nftables, policy
   routing, relay TCP через TPROXY, запуск ядер, DNS с наборами адресов;
   настройки — JSON-файлы; интеграционный тест в netns.
3. **UDP, группы и запасные, подписки, geosite/geoip** в наборах nftables.
4. **Веб-интерфейс** и вход через rpcd.
5. **Пакеты** `.ipk`/`.apk`, служба procd, sysupgrade, обновления ядер, смоук-тест в QEMU.
6. Соединения, статистика, резервная копия, kill switch при загрузке.
